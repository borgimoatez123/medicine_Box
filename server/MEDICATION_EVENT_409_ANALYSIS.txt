9. WHY THE OTHER API ENDPOINTS WORK
------------------------------------------------------------------------------
- heartbeat: Only updates MedicineBox.deviceStatus and lastSeenAt. No
  medication or drawer relationship checks. Always succeeds for a valid deviceId.

- schedule (GET): Returns schedule rows. For schedules whose medication is not
  assigned to a drawer, it returns drawerId: null (graceful). It does not
  enforce that a medication must be in a drawer, so it returns 200.

- sensor-readings: Upserts DrawerSensorState by drawerNumber within a box.
  No medication relationship involved. Succeeds as long as the drawer belongs
  to the device.

- medication-events (POST): Enforces the full integrity chain:
  box -> patient -> schedule -> medication -> drawer -> drawerMedication.
  This is the only endpoint that requires the medication in the schedule to
  match the medication physically loaded in the drawer. When that invariant
  fails, it correctly returns 409.

10. RECOMMENDED FIX
------------------------------------------------------------------------------
The fix is primarily a DATA fix, with a secondary Pi-side contract improvement.

PRIMARY (data) — Assign the schedule's medication to the configured drawer:
  Option A (correct the drawer assignment):
    Update the DrawerMedication row for drawer c77a90f8-... to point to
    medicationId 94c14b77-... ("paranormal") — ONLY if the physical drawer
    actually contains "paranormal" pills. This must be verified physically
    before changing the DB, because the servo will dispense whatever is
    physically in the drawer.

  Option B (correct the schedule):
    If the physical drawer actually contains medication 4bf7ace9-..., then
    update the Schedule.medicationId to 4bf7ace9-... so the schedule matches
    the physical contents.

  Option C (re-assign):
    Delete the current DrawerMedication (4bf7ace9-...) and create a new
    DrawerMedication linking drawer c77a90f8-... to medication 94c14b77-...
    with the correct quantity. Use the existing POST /api/drawer-medications
    endpoint or the ADMIN drawer assignment flow.

  The correct option depends on which medication is PHYSICALLY in drawer 1.
  The DB must reflect physical reality; otherwise the wrong pills dispense.

SECONDARY (Pi contract) — Stop using a hardcoded configured drawerId:
  The Pi should derive drawerId from the schedule API response, not from a
  hardcoded value. If the schedule API returns drawerId: null, the Pi should
  NOT attempt to dispense — it should surface a configuration error to the
  user (e.g., "No drawer assigned to this medication") and skip the motor
  command. This prevents the motor from running when the backend will reject
  the event.

  Specifically, in backend_orchestrator.py's _record_medication_event and
  schedule-parsing code:
    - Use schedule_entry['drawerId'] from the GET /schedule response.
    - If drawerId is null, log a configuration error and do not run the motor.
    - Do not fall back to a hardcoded configured drawer ID.

TERTIARY (backend, optional but recommended) — Improve the 409 message:
  The current message "Schedule medication does not match drawer medication"
  is accurate but does not tell the operator WHICH medication is in the
  drawer vs. which the schedule expects. For debuggability, the backend could
  log (server-side only, not in the response) the expected medicationId and
  the drawer's actual medicationId. The response message itself is fine as-is
  for security (no internal IDs leaked to the client).
