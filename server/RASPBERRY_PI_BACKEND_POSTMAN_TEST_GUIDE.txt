  GET  /api/devices/medication-events        (deviceId query, no JWT)
  POST /api/devices/sensor-readings

REAL AUTH IMPLEMENTATION (verbatim from DevicesController.ts L1–L93):

  SECURITY LIMITATION (intentional, current codebase):
    Device authentication via X-Device-Id / X-Device-Token HTTP headers
    is NOT enforced on any /api/devices/* route. There is no middleware
    that validates those headers.

  INSTEAD the device identity is resolved inside every controller method
  via resolveRequestingDeviceId(req), which returns the FIRST non-empty
  value from THIS PRIORITY ORDER:

    1. req.deviceId   (field populated by a FUTURE trusted-device
                       middleware that is NOT YET WRITTEN — today this
                       is always empty / undefined, so it is skipped)
    2. req.query.deviceId    (URL query string: ?deviceId=...)
    3. req.body.deviceId     (JSON POST body field "deviceId")

  For the heartbeat / face-verification / medication-events /
  sensor-readings POST calls:
    ALWAYS include "deviceId": "{{deviceId}}" in your JSON BODY.
    (source 3 above — this is the only source that works for POST
    requests with a JSON payload).

  For the GET calls (face-reference and schedule):
    GET /api/devices/patients/:patientId/face-reference
      ?deviceId={{deviceId}}   (because face-reference route does not
                                 contain deviceId in its URL params.
                                 Must pass as query string per source 2).
    GET /api/devices/:deviceId/schedule
      deviceId is in the URL params. resolveRequestingDeviceId also
      reads it as a fallback from validated schema param, so it works
      without query string. Adding ?deviceId= is optional but harmless.

  NO X-Device-Id HEADER IS REQUIRED OR HONORED TODAY.
  Do not waste time adding it in Postman.
  The ONLY current "auth" for device endpoints is the literal
  "deviceId" field in JSON body or query string.

  This limitation is TEMPORARY and explicitly called out in the
  controller file comment block (DevicesController.ts L1–L6).

TEST #1 — DEVICE HEARTBEAT
============================================================
Purpose:
  The Raspberry Pi calls this endpoint every <DEVICE_OFFLINE_THRESHOLD_MS
  default 5000ms. The backend sets MedicineBox.lastSeenAt = now() and
  MedicineBox.deviceStatus = ACTIVE. A separate background monitor
  DeviceOfflineMonitor flips deviceStatus back to OFFLINE if 5s pass
  without a new heartbeat.

METHOD:      POST
FULL URL:    {{baseUrl}}/api/devices/heartbeat
AUTH:        Pattern B — deviceId in JSON BODY ONLY (no JWT).
             No X-Device-Id header required.
HEADERS:
  Content-Type: application/json
BODY (raw JSON):
  {
    "deviceId": "{{deviceId}}"
  }
Real validator source: devices.validator.ts L3–L7 heartbeatSchema
  zod object strict; deviceId string non-empty. No extra keys allowed
  (strict() will throw BadRequestError on unexpected fields).

POSTMAN STEPS:
 1. Open Postman.
 2. New request.
 3. Method = POST.
 4. URL = {{baseUrl}}/api/devices/heartbeat
 5. Headers → add Content-Type: application/json.
 6. Body → raw → JSON (dropdown).
 7. Paste the JSON above.
 8. Replace {{deviceId}} with the REAL MedicineBox.deviceId
    you copied from Prisma Studio in section 2.
 9. Click Send.
10. Compare to the expected response / status below.
11. Open Prisma Studio → MedicineBox → verify the row's lastSeenAt
    is "just now", and deviceStatus = ACTIVE.

EXPECTED HTTP STATUS: 200 OK
EXPECTED RESPONSE (data inside the success envelope):
  {
    "deviceId": "{{deviceId}}",
    "status": "ACTIVE",
    "lastSeen": "2026-09-29T10:00:00.000Z"
  }
Where status comes from MedicineBox.deviceStatus field (enum
DeviceStatus = ACTIVE | OFFLINE). The "lastSeen" is always a
fresh ISO-8601 UTC timestamp on every successful call.

DATABASE EFFECT (real Prisma fields):
  UPDATE "MedicineBox"
    SET "lastSeenAt"   = now(),
        "deviceStatus" = 'ACTIVE'
    WHERE "deviceId" = {{deviceId}};
  (PrismaMedicineBoxRepository.touchHeartbeat).

VERIFICATION:
  Prisma Studio MedicineBox row for your deviceId:
    lastSeenAt timestamp advances every call.
    deviceStatus stays = ACTIVE between calls.

  Let the device sit >DEVICE_OFFLINE_THRESHOLD_MS (5s default) without
  any heartbeat call, then re-check deviceStatus. If the backend
  process is running, DeviceOfflineMonitor will set it back to
  OFFLINE after the threshold.
  (This is the actual implemented offline behavior, source:
   DeviceOfflineMonitor.ts + PrismaMedicineBoxRepository.markStaleDevicesOffline
   updateMany WHERE lastSeenAt < now() - thresholdMs → deviceStatus OFFLINE).

TEST #4 — SCHEDULE SYNCHRONIZATION (PI PULLS SCHEDULES)
============================================================
Purpose:
  Raspberry Pi (re-)downloads all medication schedules for the
  patient associated with the device's owner user. Backend is the
  source of truth. The Pi caches these times locally and uses them
  to know when to alert the patient / run face verification / open
  a drawer motor. Schedule is returned sorted ascending by each
  expanded event HH:MM string.

METHOD:      GET
FULL URL:    {{baseUrl}}/api/devices/{{deviceId}}/schedule
AUTH:        Pattern B. deviceId is in URL param (also validated via
             getDeviceScheduleSchema L25–29). No query string needed.
HEADERS:     Accept: application/json (optional).

POSTMAN STEPS:
 1. New GET.
 2. Paste URL; replace {{deviceId}}.
 3. Send.
 4. Verify schedules[] array length >= 1 (assuming data exists; see
    step 2 for setup).
 5. Within each schedule, verify drawerId, medicationId, times list.

EXPECTED HTTP STATUS: 200 OK
EXPECTED RESPONSE data:
  {
    "patientId": "REPLACE_WITH_REAL_PATIENT_ID",
    "schedules": [
      {
        "scheduleId": "REPLACE_WITH_REAL_SCHEDULE_ID",
        "medicationId": "REPLACE_WITH_REAL_MEDICATION_ID",
        "medicationName": "Ibuprofen 200mg",
        "drawerId": "REPLACE_WITH_REAL_DRAWER_ID",
        "dosageQuantity": 2,
        "startDate": "2026-09-01",
        "endDate": null,
        "daysOfWeek": [1,2,3,4,5],
        "times": [
          "08:00",
          "14:00",
          "20:00"
        ],
        "isActive": true,
        "refillReminder": true
      }

NOTES on the response (real implementation details from GetDeviceSchedule.ts):
  - times[] is derived from Schedule.timesPerDay TEXT[] array. Only
    entries matching the regex /^\d{2}:\d{2}$/ are kept (invalid times
    filtered, NOT 400-rejected; no warning emitted).

TEST #5 — MEDICATION EVENT (TAKEN or MISSED)
============================================================
Purpose:

  patient takes the pills or misses, the Pi sends this event.

============================================================

  Every poll interval (recommend 500 ms — 2s), the Pi calls this
  endpoint asking "do you have any pending commands for me?". The
  backend returns ALL rows for this device where status == PENDING,
  atomically flips their status → SENT and sets sentAt=now() inside
  a single $transaction so the SAME command is NEVER returned on a

  returns [] even if Pi calls it again instantly). Commands are
  returned oldest-first (createdAt ASC) so order is deterministic.
  Currently only command type exposed is OPEN_DRAWER (lock/unlock
  motor); future command types can be added without changing this
  endpoint shape.

             the URL / query today (the X-Device-Token middleware
             is commented-out — see DevicesController header comment).
             Do NOT add Authorization: Bearer here. This is a Pi
             endpoint, NOT a user endpoint.
HEADERS:     (none required; Content-Type not needed for GET)

 1. Populate {{deviceId}} from a real MedicineBox.deviceId record

TEST #11 — RASPBERRY PI: POST ACK COMMAND RESULT (EXECUTED or FAILED)
============================================================
Purpose:
  After the Pi hardware (servo motor / lock relay) completes the
  OPEN_DRAWER command from Test #10, the Pi POSTs the real
  hardware result back so the backend transitions status SENT ->
  EXECUTED or SENT -> FAILED. This is the ONLY code path that
  marks a command EXECUTED (Flutter in Test #9 creates PENDING;
  it never skips straight to EXECUTED — only the physical Pi
  confirms success/failure). The Pi MUST provide the body.deviceId
  that MATCHES the command.deviceId ownership: if someone sends
  the wrong deviceId (trying to hijack-ack another device's
  command) the backend returns 403 Forbidden explicitly (NOT 404
  this time; ownership here is explicit cross-device not the
  mobile-side obscurity pattern).

METHOD:      POST
FULL URL:    {{baseUrl}}/api/devices/commands/{{commandId}}/result
             ({{commandId}} must be the exact data.commands[0].commandId
              returned in Test #10's JSON — not a drawer id.)
AUTH:        None. Same trust model as Test #10. No JWT.
HEADERS:
  Content-Type: application/json

BODY (raw JSON — SUCCESS CASE, 99% of calls):
  {
    "deviceId": "{{deviceId}}",
    "status":   "EXECUTED"
  }

BODY (raw JSON — FAILURE CASE, edge e.g. motor jam):
  {
    "deviceId": "{{deviceId}}",
    "status":   "FAILED",
    "error":    "Drawer motor jammed — servo stalled 3 times, max retries exceeded"
  }
(Max error length: 1000 chars. Null/omitted error on FAILED -> stored null.)

POSTMAN STEPS:
 1. Prerequisite chain: run Test #9 (create command PENDING), then
    run Test #10 first poll (flip to SENT, you get commandId back).
    Copy that exact commandId string into Postman variable:
        commandId = <the returned commandId UUID>
 2. Build the URL with this commandId as /commands/:commandId/result.
 3. Populate body.deviceId with the SAME deviceId that owns that
    command (must match row DeviceCommand.deviceId exactly — case
    sensitive string).
 4. Send EXECUTED body. Then separately for a different commandId
    re-run steps 9 + 10 to get a new SENT command and post FAILED
    body so both branches are verified.

EXPECTED HTTP STATUS: 200 OK
EXPECTED RESPONSE envelope (both cases):
  EXECUTED case:
  {
    "status": "success",
    "statusCode": 200,
    "data": {
      "commandId": "<uuid>",
      "status":    "EXECUTED"
    }
  }

  FAILED case:
  {
    "status": "success",
    "statusCode": 200,
    "data": {
      "commandId": "<uuid>",
      "status":    "FAILED"
    }
  }

DATABASE EFFECT:
  EXECUTED: status SENT -> EXECUTED ; executedAt = now() ; error wiped -> null.
  FAILED:   status SENT -> FAILED   ; executedAt = null    ; error set to body.error (or null if not provided).
  Note: idempotent. You can send the same EXECUTED/FAILED ack twice
  and it just returns 200 again (updateResult always returns the

  NO DrawerMedication.quantity changed.
  NO MedicationSession inserted. Those only in Test #5.

18. ERROR TESTING MATRIX (status codes the implementation ACTUALLY returns)
============================================================
Only the codes below are produced by existing AppError subclasses.
The backend does NOT emit 422, 409 on validation, or other codes
outside this list (today only conflict 409 exists for insufficient
stock during medication TAKEN).

HTTP 400 Bad Request
  Source: BadRequestError class.
  Scenarios:
    * Heartbeat validator L3-7: missing deviceId, non-string, extra keys.
    * Face reference: missing patientId or deviceId.
    * Face verification payload missing a field or wrong type.
    * Schedule sync deviceId in URL is empty string.
    * Medication event: invalid TAKEN/MISSED quantity rules.
    * Sensor reading: humidity outside 0..100, temperature non-finite,
      fireDetected non-boolean, any extra keys due to schema .strict().

HTTP 401 Unauthorized
  Source: UnauthorizedError class (authMiddleware.ts).
  Scenarios:
    * Pattern A endpoint (/api/medicine-boxes/:id/sensors or /api/drawers)
      called WITHOUT Authorization: Bearer header: "No token provided".
    * JWT expired / malformed / wrong signature.
    * Login with wrong password: "Invalid credentials".

HTTP 403 Forbidden
  Source: ForbiddenError class.
  Scenarios:
    * requireRole middleware mismatch (e.g. USER calls POST /api/medicine-boxes/
      which is requireRole ADMIN). For device endpoints: use-case ownership
      gates: deviceId + patientId mismatch; drawerId from another box; etc.
    * Face reference / face verification / medication event / sensor post
      all cross-validate that the resource belongs to the device owner user.

HTTP 404 Not Found
  Source: NotFoundError class (used in every use-case on findById return null,
  plus deviceId → MedicineBox lookup; drawerId → Drawer lookup; patientId →
  Patient lookup).
  Scenarios:
    * Heartbeat / schedule-sync: nonexistent deviceId.
    * Face reference: nonexistent patientId OR patient has no avatar.
    * Medication event: nonexistent scheduleId / patientId / drawerId.
    * Sensor reading: nonexistent deviceId OR drawerId.
    * Mobile sensor GET: MedicineBox.id not found OR Drawer.id not found.
    * Mobile sensor GET: JWT user is NOT the owner (security by obscurity
      → 404, not 403).

HTTP 409 Conflict
  Source: ConflictError class.
  Scenarios:
    * TAKEN medication event: DrawerMedication.quantity < quantityTaken
      ("Insufficient quantity...").
    * (Other 409s in the CRUD endpoints are out of scope for RPi guide.)

HTTP 500 Internal Server Error
  Source: errorMiddleware.ts catch-all.
  Scenarios (intentional; only for real bugs never caught by above):
    DB connectivity issues (P1001 / P1002), unexpected runtime exceptions.
    RPi endpoints should never return 500 under normal conditions.

19. GET /api/devices/medication-events  (Medication Event History)
============================================================
A read-only endpoint that returns MedicationSession records
(sorted by scheduledAt DESC) with optional filters and
pagination. Supports TWO callers:

  A) Mobile (JWT auth):
       Authorization: Bearer {{token}}
       (optionally also pass deviceId/patientId/etc. filters)
     -> Results are scoped to patients owned by the JWT's userId.

  B) Raspberry Pi (no JWT):
       Pass ?deviceId={{deviceId}}
     -> Results are scoped to that single device.

If neither a Bearer token NOR a deviceId query param is provided,
the server returns HTTP 401 Unauthorized.

QUERY PARAMETERS (all optional, validated strictly):
  deviceId    string   filter by device (drawer.medicineBox.deviceId)
  patientId   string   filter by patient
  scheduleId  string   filter by medication schedule
  drawerId    string   filter by drawer
  status      string   TAKEN | MISSED | PATIENT_TAKEN | PATIENT_SKIPPED |
                       FACE_RECOGNITION_FAILED | DISPENSING_FAILED |
                       DEVICE_FAILURE
                       (TAKEN maps to DB result PATIENT_TAKEN)
  limit       int      1..100 (default 20, max 100)
  offset      int      >= 0   (default 0)

UNKNOWN query parameters are rejected with HTTP 400.

EXAMPLE REQUESTS:

  Mobile (JWT) — all events for the caller's patients:
    GET {{baseUrl}}/api/devices/medication-events
    Header: Authorization: Bearer {{token}}

  Mobile (JWT) — only TAKEN events for one patient:
    GET {{baseUrl}}/api/devices/medication-events?patientId={{patientId}}&status=TAKEN
    Header: Authorization: Bearer {{token}}

  Raspberry Pi — events for one device, paginated:
    GET {{baseUrl}}/api/devices/medication-events?deviceId={{deviceId}}&limit=20&offset=0

EXPECTED RESPONSE (HTTP 200):
  {
    "status": "success",
    "statusCode": 200,
    "data": {
      "events": [
        {
          "id": "uuid",
          "deviceId": "DEV-BOX-...",
          "patientId": "uuid",
          "scheduleId": "uuid",
          "drawerId": "uuid",
          "medicationId": "uuid",
          "status": "TAKEN",          // TAKEN | MISSED | raw MedicationSessionResult
          "quantityTaken": 1,
          "quantityBefore": 20,
          "quantityAfter": 19,
          "scheduledAt": "2026-10-13T06:00:00.000Z",
          "completedAt": "2026-10-13T06:00:05.000Z",
          "createdAt": "2026-10-13T06:00:00.000Z",
          "occurrenceDate": "2026-10-13",
          "occurrenceTime": "06:00"
        }
      ],
      "pagination": {
        "limit": 20,
        "offset": 0,
        "total": 1
      }
    }
  }

NOTE: quantityTaken = quantityBefore - quantityAfter (0 for MISSED).
      status TAKEN  <-> DB result PATIENT_TAKEN
      status MISSED <-> DB result MISSED

NEGATIVE TESTS:
  - No token + no deviceId -> HTTP 401 Unauthorized
  - Invalid Bearer token    -> HTTP 401 Unauthorized
  - limit=0 or limit=101    -> HTTP 400 Bad Request
  - offset=-1               -> HTTP 400 Bad Request
  - status=INVALID          -> HTTP 400 Bad Request
  - Unknown query param     -> HTTP 400 Bad Request
